# ADR-0012: The `faststudio` command-line interface

- Status: Accepted (2026-11-25, maintainer approval with amendments A1–A7)
- Date: 2026-11-24
- Plan: docs/plans/v0.2.md

## Context

v0.1 asks users to copy a `create_admin.py` script. Recovering from a lockout
(ADR-0009) and setting up permissions also need a supported tool.

## Decision

1. **Console script** `faststudio`, built on stdlib `argparse`, with no new
   dependency. Commands:
   - `faststudio createadmin --app module.path:admin [--username U] [--set field=value ...]`
   - `faststudio changepassword USERNAME --app module.path:admin`
   - `faststudio syncpermissions --app module.path:admin [--dry-run] [--prune [--yes]]`
2. **`--app`** imports `module.path` and takes the attribute after `:`. That
   is either an `Admin` instance or a zero-argument callable returning one
   (app factories). Errors are short messages with no tracebacks, as in the
   v0.1 example CLI.
3. **Passwords** are read only through `getpass`, twice, and compared. They
   are never accepted from argv or environment variables. They are checked by
   the backend's validators (`user_admin.validators`) before hashing.
   - If stdin is not a TTY, the command refuses with exit code 2, because
     `getpass` would otherwise echo the input.
   - Tests inject a password-reader callable.
4. **User management** goes through the backend's `user_admin` capability
   (ADR-0011), whose methods take an `AsyncSession`. Backends without it give
   a clear error naming the capability.
   - `ModelUserBackend` implements it. `createadmin` sets `is_admin` and
     `is_active`. It prompts for the username and for every required column
     without a default (the README model's `email`); `--set field=value`
     supplies other values, and missing ones fail with a message naming the
     columns.
   - `contrib.auth` sets `is_superuser`.
   - The CLI never creates tables. If the table is missing, it says to run
     the migrations or `create_all` first.
5. **`syncpermissions`** is idempotent.
   - It creates the missing `<identity>.<action>` permissions and the
     `extra_permissions`, and updates their names. An `IntegrityError` from a
     concurrent worker is tolerated.
   - `--dry-run` lists missing, stale and orphaned codenames.
     - **Stale:** in the database but no longer produced by any registered
       model action or `extra_permissions` entry, including codenames left
       behind by a renamed `identity`.
     - **Orphaned:** a stale codename that still has assignments.
     - Renaming an identity makes its old codenames stale; this is
       documented.
   - It never deletes anything unless `--prune`. `--prune` deletes only stale
     codenames, together with their assignments, after listing them. It asks
     for confirmation by default; `--yes` skips the prompt for CI. Without a
     TTY and without `--yes` it refuses. Passwords are never
     non-interactive.
   - `Admin(sync_permissions_on_startup=True)` runs it lazily on the first
     request, under an `asyncio.Lock` created inside the running loop,
     because mounted sub-apps get no lifespan events. It never prunes. A
     failed sync is logged and retried on a later request; requests keep
     being served, and missing grants fail closed.
6. **Each command runs in a single `asyncio.run`** and disposes the engine.
   Database errors print only the exception type, as in v0.1.

## Consequences

- The README and `examples/basic` switch to the CLI. The `create_admin.py`
  and `restore_admin.py` snippets stay in getting-started under "Without the
  CLI" for v0.2, still tested, and are removed in v0.3.
- The CLI is a supported recovery path for locked-out installations.

## Amendment (M18a, 2026-11-25)

The capability named `user_admin` above shipped as `BackendCapabilities.accounts`
(`AccountManager`); its validators are `accounts.password_validators`. The name
avoids clashing with the usual `ModelAdmin` subclass `UserAdmin`. See ADR-0011
"Implementation notes (M18a)".

## Amendment (M19, 2026-11-25)

- **Commands as shipped:** `createadmin`, `changepassword`, `syncpermissions`
  and, at the maintainer's request, `checkusers` (reports and, with `--fix`
  plus confirmation or `--yes`, repairs drift of contrib's normalized
  usernames; non-zero exit while problems remain). It uses a new optional
  capability, `BackendCapabilities.username_audit` (`UsernameAudit`).
- **Accounts:** `AccountManager` gained `find_account`, `required_fields`
  and `create_admin` (before the protocol is released). `--set` supplies
  text columns only; a required non-text column without a default makes
  `createadmin` fail, naming it.
- **Permission names:** `PermissionSchema.name_field` (contrib: `name`);
  names are "Can <action> <name_plural>" or the `extra_permissions`
  description.
- **Startup sync** is an ASGI wrapper around the admin sub-app only; it
  needs a permission schema (`ConfigurationError` otherwise).
- **Exit codes:** 0 success, 1 refused or failed, 2 usage error.
- `examples/basic` keeps its own `create_admin` module: its `create_app()`
  returns the FastAPI app, not an `Admin`, so it is not an `--app` target.

## Amendment (v0.2 item 2, 2026-11-26)

This amendment supersedes the parts of §2, §5 and the M19 amendment named
below. The text above is kept as it was approved.

- **§2, `--app` targets.**
  - `--app` may also name a FastAPI application, or a zero-argument factory
    returning one. The CLI then uses the `Admin` mounted on that
    application, directly or on one of its mounted sub-applications.
  - Exactly one must be found. With none or several, the command exits 2:
    the message lists the mounts it found (base URL and title), or says that
    an `Admin` created in the lifespan is not seen.
  - The `Admin` is found through a private back-reference on its own `Mount`
    route. That reference lives exactly as long as the application, and
    nothing is added to `app.state`.
  - **The application's lifespan never runs.** The CLI imports, and calls a
    factory, but never starts the application. Anything the lifespan
    configures (for example a database URL fetched from a secrets manager)
    is not seen, and the CLI still never creates tables.
  - A factory is called only if it takes no arguments (checked with
    `inspect.signature`). An exception raised while it runs is reported by
    type, as `Calling module:attr() failed (Type).`
- **Recovery (Consequences).** "A supported recovery path" means the CLI
  restores access by creating a new admin (`createadmin`) or setting a
  password (`changepassword`). It never changes an existing account's
  active or admin flags, so it does not re-enable a disabled account.
- **`examples/basic`** (supersedes the M19 bullet). The example is an `--app`
  target (`examples.basic.app:create_app`). Its `create_admin` module is
  kept only to restore a locked-out account (re-enable it, restore admin
  rights, optionally reset the password), which the CLI does not do.
- **§5, startup sync with several processes.**
  - Duplicate inserts are skipped by the insert itself. On MySQL/MariaDB the
    `ON DUPLICATE KEY UPDATE` assigns the codename to itself, a no-op. That
    way a row matched through another unique index (for example a unique
    name) is never re-keyed.
  - After inserting, the sync checks that every expected codename exists,
    and fails otherwise (CLI exit 1, nothing changed). On MySQL/MariaDB this
    check is a locking read (`LOCK IN SHARE MODE`), which sees codenames
    another worker committed after this transaction's snapshot.
  - A deadlock victim or serialization failure is retried after a short,
    jittered backoff: at most 5 attempts, and none started more than 2
    seconds after the first, without logging.
  - Lock-wait timeouts, and every other error, keep the original behaviour:
    logged by type and retried on a later request after 30 seconds.
